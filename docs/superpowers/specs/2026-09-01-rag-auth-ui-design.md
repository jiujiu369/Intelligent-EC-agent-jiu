# RAG 统一 768 维与账号安全、使用说明设计

## 目标

在保留主、备用两套独立 ChromaDB 的前提下，将两套嵌入模型统一为 `bge-base-zh-v1.5`（768 维）；同时为本地账号系统增加安全问题、找回密码、修改密码，并在 Gradio 买家和商家界面提供对应使用说明。

## 范围

- 修改 `config.py`、`embedding/rag_pipeline.py`、`tools/auth_login.py`、`web_ui.py`。
- 修改或新增与本次功能直接相关的测试。
- 不修改 Agent 工具调用、商品与政策检索顺序、会话隔离、RBAC 和其他业务流程。
- 保留工作区内已有的无关修改。

## RAG 双库设计

- 主模型继续读取 `AGENT_RAG_PRIMARY_MODEL`，备用模型继续读取 `AGENT_RAG_FALLBACK_MODEL`；两者默认值均为 `bge-base-zh-v1.5`。
- 主库继续使用 `datas/chroma_db` 和 `customer_service_docs`。
- 备用库使用新目录 `datas/chroma_db_fallback_768` 和新集合 `customer_service_docs_fallback_768`，不读取旧 384 维库，避免 Chroma 集合维度冲突。
- 主、备用模型复用同一套加载与初始化函数，不添加模型专属 Pooling 或维度修补逻辑。
- 删除脚本中的 MiniLM、384 维、`fallback-384` 和备用入库函数的 `_384` 命名，统一使用 `fallback-768` 与 `_fallback`。
- 政策和商品文档分别写入主库及备用库；检索顺序保持主库、备用库、关键词兜底。
- 旧 `datas/chroma_db_384` 数据不删除，只是不再使用，便于用户自行备份或清理。

## 账号安全设计

### 数据结构

新账号在原有 `password_hash`、`salt`、`created_at` 基础上增加：

- `security_question`：固定问题文本。
- `security_answer_hash`：安全答案的 PBKDF2-SHA256 哈希。
- `security_answer_salt`：安全答案的随机盐值。

密码和安全答案均不保存明文。安全答案比较前统一去除首尾空白并转为小写，降低大小写误输影响。

### 注册与旧账号兼容

- UI 和 CLI 注册必须选择固定安全问题并填写答案。
- 旧账号缺少安全问题时仍可正常登录和修改密码。
- 旧账号登录后可通过当前密码补设安全问题；已设置的账号也可用相同流程更新问题和答案。

### 找回密码

1. 用户选择角色并输入用户名。
2. 系统返回该账号的安全问题；账号不存在或未设置时返回明确但不包含敏感数据的错误。
3. 用户提交安全答案、新密码和确认密码。
4. 验证成功后生成新的密码盐和哈希并持久化。

### 修改密码

- 登录用户提交旧密码、新密码和确认密码。
- 验证旧密码及新密码格式后生成新的盐和哈希。
- 修改成功后当前登录状态保持不变。

## Gradio 界面设计

- 登录页增加“忘记密码 / 找回密码”折叠区域，分为获取安全问题和回答问题重设密码两个动作。
- 主界面右侧增加“账号安全”折叠区域，提供修改密码以及设置或更新安全问题。
- 主界面右侧增加“使用说明”折叠区域，登录成功后按角色更新内容：
  - 买家：商品查询、订单查询、售后申请和会话管理示例。
  - 商家：商品与库存查询、商品修改、销售报表、运维面板示例。
- 使用说明提供可直接复制的自然语言示例，不改变聊天主流程。

## 错误处理

- 角色、用户名、密码、安全问题和答案均执行输入校验。
- 新密码必须满足现有最低长度规则，且两次输入一致。
- 用户文件写入失败时不报告成功。
- 模型或 ChromaDB 初始化失败时沿用现有降级标志和日志流程。

## 测试与验收

- 先编写失败测试，覆盖安全问题注册、旧账号兼容、修改密码、找回密码及错误答案拒绝。
- 覆盖主、备用模型默认值、环境变量读取、独立 768 维库路径和 `fallback-768` 标识。
- 覆盖主、备用政策及商品入库入口仍分别调用独立集合。
- 对修改文件执行编译检查，并运行相关认证与 RAG 测试。
- 检查本次改动中不再出现 MiniLM、`fallback-384` 或备用函数 `_384` 标识。
